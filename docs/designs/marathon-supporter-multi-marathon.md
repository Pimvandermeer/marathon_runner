# Design: Marathon Supporter, from Rotterdam-only toy to multi-marathon planner

Generated by /office-hours on 2026-10-14
Branch: main
Repo: Pimvandermeer/marathon_runner
Status: APPROVED
Mode: Startup

## Problem Statement
Supporters of a marathon runner want to see their runner more than once along the course. In the week before the race the runner builds the plan for them by hand: which metro stop, what time, based on wave and goal pace. That plan is tedious to make and breaks as soon as the pace or wave changes. Marathon Supporter computes passing times at transit-accessible spots from wave plus goal pace and gives the runner a share link. Today it only works for Rotterdam 2025, with hand-typed kilometre marks and a static JPG map, and the data is a year stale.

The user's framing, in their words: "the official app is for race day. this site helps living up to the day where they know where they can stand if their runner has a certain tempo in mind."

## Demand Evidence
- Used at Rotterdam 2025 by friends of runners. The user "got feedback that people really liked it".
- Nobody has paid. Nobody has been watched using it live.
- Classification: interest, not demand. The first demand test is a runner building and sharing a plan unprompted and tipping afterwards.

## Status Quo
"Runner plans for them." The runner works out a pace chart in taper week and tells supporters where to stand. The organizer's app covers race day only. Cost of the status quo: runner stress in taper week, supporters seeing the runner once instead of three or four times.

## Target User & Narrowest Wedge
- User: a Dutch marathon runner in taper week with three to ten supporters, running Rotterdam, Amsterdam or Den Haag. Not yet a named person. Naming one is part of the assignment.
- Wedge chosen: the runner gets a share link and a Tikkie or Ko-fi ask. Zero friction, low money. Its value is evidence, not revenue.
- Real money, later: an organizer or transport operator paying per edition for a branded planner. Mid-size European marathons lack the NYRR-style app budget that bundles spectator itineraries into the official app.

## Constraints
- Solo builder. Amsterdam Marathon is on Sunday 2026-10-18 (corrected in the eng review from 2026-10-19; organiser programme page read 2026-10-14), four days from this session. Den Haag follows.
- Static hosting. The Express, Drizzle and Postgres code in the repo is unused and will be removed.
- Live site today is a manual upload of static-build to an Apache shared host. The GitHub Pages workflow has never run and uses retired action versions. The .com domain redirects to the personal .nl subdomain.
- Traffic is a one-day-a-year spike. Live calls to Overpass or the public OSM tile server on race morning are not acceptable.
- No organizer relationship. Using official names and logos implies affiliation.
- GDPR applies the moment analytics or accounts appear.
- Correctness is non-negotiable (owner, mid-session): a wrong wave time or a stop on the wrong side of the course sends a family to the wrong place on race day. Every published data value is verified, see Data Verification.

## Premises
1. The runner is the user. They build the plan and share it; supporters consume it. Agreed.
2. Race day belongs to the organizer's app. The site never competes on live tracking. Agreed.
3. Doing nothing means a Rotterdam-only toy that rots yearly, because waves and dates change per edition. Accepted on evidence: the config still says 2025.
4. A static site with committed per-edition data packs is enough. No backend. Accepted on evidence: all math runs in the browser, the share link carries the whole plan. Two triggers would reverse this: an organizer wants to edit their own page, or hand-editing packs for more than five or six races a year becomes the pain.
5. Tips now, organizers later. Agreed.

Ruled out during the session: a backend now (no state to store), user-uploaded GPX (visitors never have one), consumer ads (one-day traffic).

## Approaches Considered
### Approach A: Amsterdam by hand, this week
Keep the current code. Add an Amsterdam 2026 pack by hand (date, waves, ten to twelve metro and tram stops with kilometre marks), re-enable the marathon selector, add the tip link, fix the GitHub Pages deploy, make marathon-supporter.com canonical. Effort S (human about 2 days, Claude Code about 1 hour plus a DNS change). Risk low. Completeness 5/10: still hand-typed kilometre marks, static JPG map, translation hack untouched.

### Approach B: GPX pack pipeline
A script takes a GPX and a buffer distance, pulls stations and stops from OpenStreetMap via Overpass once at build time, projects each stop onto the route returning every pass for loops like Slinge, and writes a pack per edition. Leaflet map with the route and stops drawn from local GeoJSON. Base map tiles default to self-hosted PMTiles of the city extent served as static files next to the site, so race morning makes no third-party map calls; a free-tier provider is used only if the PMTiles for a city exceed the hosting size limit, and that choice is made in B's plan against expected race-day opens. In every case the map is optional: the stop list and passing times never depend on tiles, and if tiles fail to load the map container hides without an error. Marathon in the URL path. Per-language description fields. Effort M (human about 2 weeks, Claude Code about 1 day over a few sessions). Risk medium: Overpass stop quality per city, loop handling, range-request support for PMTiles on the host. Completeness 9/10.

### Approach C: Runner share card first
Reframe the home page around the runner: name, wave, goal, then a WhatsApp-ready plan with the tip ask at the end of the runner's flow. Cookie-free analytics on link opens to measure shares per runner. Effort S to M. Risk medium: a redesign of a flow nobody has watched yet. Completeness 6/10.

## Recommended Approach
A now, then B. C is built only if both conditions in the Success Criteria hold by 2026-10-26: at least two runners watched and five or more tips. Rationale: the goal is a startup and there is zero observation evidence. Amsterdam in five days supplies real runners for free. B starts immediately after Amsterdam with its own deadline of 2026-11-15, chosen so the pipeline exists before any spring 2027 race and while the Amsterdam data work is fresh. Den Haag's date is unconfirmed; if it falls before B is done, Den Haag gets an A-style hand-verified pack, and B regenerates it afterwards as a pipeline test. Cut corners in A are logged as a shortcut with the upgrade trigger "Amsterdam has run".

Scope of A, concretely:
- Remove server/, the DB schema, Drizzle config, Replit config, and the committed build folders (dist, docs build output, static-build). One Vite config.
- Pages workflow on current action versions and Node 20. CNAME becomes marathon-supporter.com. Cutover order is in the Distribution Plan.
- Amsterdam 2026 pack: date, wave times from the organizer's site, stops with kilometre marks and coordinates, spectator tips in Dutch and English. "Coming soon" text removed.
- Share links carry the marathon. Today the link holds only name, wave and pace, and the receiving page reads the marathon from the sender's localStorage default, so an Amsterdam plan would open as Rotterdam. A adds a marathon parameter to every generated link and the loader selects that pack. A link without the parameter can only be a pre-A Rotterdam 2025 link, so it opens the site with no plan loaded and a notice in Dutch and English that the link is from a previous edition and a new plan must be made. A link naming an unknown or unpublished marathon shows the same kind of error. A link whose wave does not exist in the selected pack shows an error, never a default wave. When a pack ships in the start-time fallback mode (see Data Verification), the link carries the entered start time instead of a wave, the receiving page computes from that time, and such links keep working after the pack switches to wave mode because a start time in the link takes precedence over a wave.
- Rotterdam 2025 is hidden during A. Its waves and date are a past edition and fail Data Verification. The selector lists only verified upcoming editions, so with one pack it renders as a label, not a dropdown. Rotterdam returns as the 2027 edition through B.
- Tip link in the footer and in the share dialog. It renders only when a tip URL is configured; with no URL there is no link, not a dead one. The owner supplies the URL by 2026-10-16.
- Location descriptions become per-language objects (Dutch and English) in the pack for Amsterdam. Rotterdam follows in B.

### Data Verification (applies to A and B)
- Every pack value has a recorded source: URL, date checked, and the value as read. Course kilometre marks come from the official course map. Stop coordinates come from OpenStreetMap or the operator's stop list.
- Single-source values (race date, wave start times): the organizer's official page is authoritative. The second check is an independent re-read of that page by a second agent on a different occasion, plus a search for any secondary mention (registration email text, news item). Both reads are recorded with URL and timestamp. If the two reads disagree, publishing blocks until the owner resolves it. The organizer page is re-read daily until race day; any change triggers a pack update and redeploy.
- If wave start times are not published by the go/no-go date, the pack ships without a wave selector: the page shows "start times not yet confirmed by the organizer" and the runner enters their own start time from their confirmation email. Passing times are then computed from that entry. No pack ever ships with wave times copied from a previous edition.
- Per transit stop, the record holds: the OpenStreetMap node id and coordinates, every passing kilometre the course map shows for that location, the street the course uses at that kilometre, which side of that street the stop exit lands on, whether reaching the course requires crossing it (flagged "cross before closures"), and the walking distance in metres to the spectator spot. A second agent re-derives the kilometre and the side from the course map independently. Any disagreement blocks the stop. The stop list and the shared plan render, in Dutch and English, the side of the course the stop exit lands on, the "cross before closures" warning when set, and the walking distance in metres. The OpenStreetMap id and the verifiers' notes stay in the pack file.
- Loop passes (a stop the course passes twice) are listed with every passing kilometre, never one.
- Nothing ships with a placeholder value. If a stop cannot be fully verified, the stop is left out and the gap is reported to the owner.

## Distribution Plan
Web only. GitHub Actions builds on push to main and deploys to GitHub Pages. Share links are the user-facing distribution: the runner sends one WhatsApp message.

Cutover, in order. Only one copy of the site is live at any time; the Apache host is the fallback, never a second live copy.
1. 2026-10-15: Pages workflow green. Pre-merge verification is the pull-request build-and-test check plus a local `npm run build && npx vite preview`; the pages.github.io project URL is NOT usable for verification because the site builds with a root base path and the CNAME file is ignored by Actions deploys. Live verification happens at marathon-supporter.com once the custom domain is set in repo settings (step 2), after which the project URL redirects there.
2. 2026-10-15: owner records the current .com DNS record (the Apache redirect) and its TTL, lowers the TTL to 300 seconds, waits for the old TTL to expire, then points marathon-supporter.com at GitHub Pages and sets the custom domain in the repo settings.
3. 2026-10-16, 18:00, go/no-go. Go: marathon-supporter.com resolves to the Pages site over HTTPS. The owner immediately changes the .nl subdomain on the Apache host into a redirect to the .com, so Pages is the only live copy and every redeploy reaches all visitors. No-go: the owner reverts the .com DNS to the recorded Apache redirect record; with the 300 second TTL the revert is effective within minutes, before 2026-10-17. Race week then runs on the Apache .nl site.
4. No-go branch only: the verified Amsterdam build is uploaded to the Apache host by hand by the owner before 2026-10-17, and every later pack update (for example a wave change found by the daily re-read) counts as deployed only after the owner has re-uploaded it to Apache. The Pages site stays reachable at the pages.github.io address but is not advertised.
5. Go branch: the .nl redirect stays on the Apache host for at least twelve months so links shared to the .nl address keep working; Apache is retired after that. No-go branch: steps 2 and 3 are repeated after race week, and step 5 applies once the .com resolves to the Pages site over HTTPS.
